Descripción del taller

Caso de negocio: una empresa aplica un ajuste salarial extraordinario a empleados que cumplen reglas de negocio específicas según la variante asignada. El taller evalúa criterio técnico: no basta con SQL correcto, hay que analizar datos, decidir elegibles, prevalidar el impacto económico y ejecutar con control transaccional dejando evidencia de auditoría.

Variante 3 — Ajuste conservador: los parámetros (departamento excluido, antigüedad mínima, umbrales de brecha, porcentajes de ajuste y tope máximo) se leen dinámicamente de la tabla T1_VARIANTS. No se usan valores fijos en el SQL.

Etapa 1 — Consulta diagnóstica

DENSE_RANK() OVER Subconsultas escalares LEFT JOIN como EXISTS MONTHS_BETWEEN

Retrato completo de cada empleado antes del cambio: promedio/máximo/conteo del departamento via subconsultas escalares correlacionadas, historial reciente via LEFT JOIN y ranking salarial con función de ventana.

SELECT e.employee_id, e.first_name, e.salary, -- Promedio departamental: subconsulta escalar correlacionada (SELECT ROUND(AVG(salary), 2) FROM t1_employees WHERE department_id = e.department_id) AS dept_avg_salary, -- Brecha % hacia el promedio ROUND( (dept_avg - e.salary) / NULLIF(dept_avg, 0) * 100 , 2) AS pct_gap_to_avg, -- Historial reciente: LEFT JOIN reemplaza a EXISTS CASE WHEN jh.employee_id IS NOT NULL THEN 'SI' ELSE 'NO' END AS recent_job_history_flag, -- Ranking salarial dentro del departamento DENSE_RANK() OVER ( PARTITION BY e.department_id ORDER BY e.salary DESC ) AS salary_rank_in_dept FROM t1_employees e LEFT JOIN t1_departments d ON d.department_id = e.department_id LEFT JOIN ( SELECT DISTINCT employee_id FROM t1_job_history WHERE start_date >= ADD_MONTHS(SYSDATE, -(SELECT recent_job_history_months FROM t1_variants WHERE variant_id = &p_variant_id)) ) jh ON jh.employee_id = e.employee_id ORDER BY e.department_id NULLS LAST, salary_rank_in_dept;

Etapa 2 — Decisión de elegibles

CASE WHEN encadenado T1_VARIANTS dinámico

Evalúa en orden de prioridad cada regla de exclusión. Los parámetros se leen de T1_VARIANTS — nunca se hard-codean.

-- Fragmento del CASE de elegibilidad CASE WHEN e.department_id IS NULL THEN 'NO_ELEGIBLE' WHEN e.department_id = (SELECT excluded_department_id FROM t1_variants WHERE variant_id = &p_variant_id) THEN 'NO_ELEGIBLE' -- depto excluido WHEN ds.dept_employee_count < 3 THEN 'NO_ELEGIBLE' -- depto pequeño WHEN TRUNC(MONTHS_BETWEEN(SYSDATE, e.hire_date)/12) < (SELECT min_years_service FROM t1_variants WHERE variant_id = &p_variant_id) THEN 'NO_ELEGIBLE' -- poca antigüedad WHEN jh_reciente.employee_id IS NOT NULL THEN 'NO_ELEGIBLE' -- historial reciente WHEN mgr.employee_id IS NOT NULL OR e.job_id LIKE 'AD_%' THEN 'NO_ELEGIBLE' -- manager/directivo WHEN pct_gap <= 0 THEN 'NO_ELEGIBLE' -- ya supera promedio ELSE 'ELEGIBLE' END AS eligibility_flag

Resumen económico Control de topes

Propiedades ACID — Justificación técnica

Atomicidad

El INSERT de auditoría y el UPDATE son una unidad cubierta por el SAVEPOINT. Si la validación detecta un tope superado, el ROLLBACK TO SAVEPOINT revierte ambas operaciones al mismo tiempo — nunca puede quedar una sin la otra.

Consistencia

Antes del COMMIT se verifica que ningún salario actualizado supere el 118% del promedio original del departamento. El promedio se reconstruye combinando salary_before de la auditoría con los salarios no modificados.

Aislamiento

Oracle garantiza read consistency: otras sesiones ven los salarios originales hasta el COMMIT. El bloqueo a nivel de fila impide que dos sesiones actualicen el mismo empleado simultáneamente.

Durabilidad

El COMMIT escribe primero en el redo log antes de confirmar. Si el servidor falla después del COMMIT, Oracle recupera los cambios al reiniciar mediante el mecanismo de media recovery.
